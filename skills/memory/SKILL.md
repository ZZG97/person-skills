# Memory

Keep useful context and move tracked matters forward. Every fact has one authoritative
owner: matter status and next actions live in the ledger; reference documents hold
background and knowledge; journals hold history; indexes point to those owners.

`HOME_ROOT` means the user's chosen Agent Home, not the operating system's home or
this Skill's installation directory. Resolve it from the current workspace's memory
router and information architecture, or the machine-local notes. If several homes are
plausible, ask which one. `DATA` is the data directory printed by `pledger status`.
Read `DATA/config/local-notes.md` if present; it records this environment's paths,
allowed information sources, delivery method and timezone. Do not copy those values
into the portable Skill.

`pledger` is the shim created by setup. Without it, run
`python3 <this Skill>/scripts/ledger.py`. Keep the existing config and data directory
when upgrading; the command and data format remain compatible with personal-ledger.

## Ownership

- A matter is something the user wants tracked: an errand, a decision, something
  awaited, or a technical/project task. Keep its disposition, next actions, deadlines
  and follow-up in one ledger item. Use categories to group matters, not to choose
  a second storage backend. An idea or paused plan can be `observe` with no follow-up.
- Store preferences, system facts, knowledge and substantial project background in
  the Home's reference files. An item may link to a document; the document points
  back by item ID and does not maintain the item's current status or next action.
- When an existing project tracker already owns a task, keep its status there and
  use a `transferred` ledger pointer. Create a separate item only for a distinct
  obligation the user wants this agent to manage.
- Journals may describe dated events and decisions, with item/source references.
  They are not used as the current-state owner. Priority lists contain ordering and
  links; rendered `DATA/views/` pages are generated by the program.

For example, a service configuration belongs in a system document, while deciding
whether to renew it belongs in an item that links to that document. Updating both
is appropriate when they carry different facts. Never create a second current-state
copy because the user used another phrase or because a scheduled run is writing.

## Boundaries

- Record authorized, useful updates in the current turn; first look for an existing
  owner. Do not invent tracked work from an incidental question.
- Read only available sources the user has allowed. A channel named in an example
  is not a required integration or permission to connect it.
- Scheduled follow-up checks are read-only outside the memory store. Replies,
  purchases, bookings and other actions toward third parties require the user's
  instruction for that action. Follow-up authorization is not execution authority.
- Keep personal data out of repositories and sync/backup services the user has not
  chosen. Never store credentials or identity-document numbers in notes or items.
- Change items through `pledger apply-updates`, never by editing JSON or generated
  views. Instructions reduce semantic duplication; program validation cannot prove
  that two differently worded items describe different matters.
